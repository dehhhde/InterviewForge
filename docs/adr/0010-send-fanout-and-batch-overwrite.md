# ADR-0010：出题层的扇出形状——`Send` + 批次覆盖、引用按来源核对、评审独立槽位

日期：2026-10-20
状态：部分被 **ADR-0015** 取代（2026-10-24）——"评审顺序 / 质量门 / 缺题批注 / 预算用尽"
四行以及理由 5、6 已作废：`review` 不再拦门，批注只标注哪几题有问题，题目一律照常落库。
**仍然有效**的部分：扇出粒度、`Overwrite` 与批次、题号在扇出前算、`GenerateJob` 载荷清单、
引用按来源核对、两套闸门共用 `evidence_problem`、难度由槽位盖章、独立评审槽位。
相关：`app/agents/nodes/{generate_node,review_node}.py`、`app/agents/workflow.py`、
`app/agents/state.py`、`app/services/{question_service,review_service}.py`、
`app/prompts/templates/v1/{generate,review}.{system,user}.j2`、
`scripts/probe_send_fanout.py`、`scripts/run_e2e_live.py`、
计划书 M5 与 §6 风险 5/6、ADR-0007（持久化层）、ADR-0009（确定性分工）

## 背景

`generate` 要一次性产出 15 道题（每题带题干、参考答案、评分标准、追问），`review` 要在它们
里挑硬伤并决定是否重做。四件事在这条链上互相拉扯，逼出下面这份形状：

1. **一次调用装不下**。`settings.llm.default_max_tokens = 2048`，15 题的完整输出必然截断；
   而一次长输出里任何一处 JSON 破损会让整批归零——失败面太大，重试也太贵。
2. **风险 5**：`questions` 一旦变成并行分支共享的通道，回退重做就会把新旧两批叠在一起。
   计划书要求"扇出前先把这个机制验掉"，所以它先用 `scripts/probe_send_fanout.py` 单独实测。
3. **风险 6**：出题与评审不能复用同一次思考，否则评审只是在给自家答案盖章。
4. **验收口径是比例而不是条数**：带可回溯引用 ≥ 90%、`trace` 里看得见每次回退。
   这三条数字都必须能从真简历的一次运行里读出来，不能只在替身测试里成立。

## 决策

| 环节 | 选择 | 被否决的方案 |
|---|---|---|
| 出题粒度 | 一条 `plan.items` 槽位 = 一次调用，`Send` 按配额表动态派发 N 个分支 | 一次调用出全部 15 题（token 装不下，且一处破损整批归零） |
| 累积与清空 | `questions` 用 `operator.add` 累积；扇出节点写 `{"questions": Overwrite([])}` 整批换掉旧批次 | 每轮换新通道名（报告读不到"上一版"，`trace` 也解释不了回退） |
| 题号 | `order_index` 在扇出**之前**用 `count` 累加算好，分支各拿一段 `order_start` | 按分支完成顺序编号（并行调度决定顺序，报告里的题号每次都不一样） |
| 批次 | `question_batch` 通道由扇出节点自增，落库带 `(interview_id, batch, order_index)` | 只留最新一题表（丢掉"上一版为什么被否"的痕迹） |
| 分支输入 | 出题要的一切都装进 `GenerateJob` 载荷（`plan_item` / `raw_text` / `jd_text` / `parsed` / `roster` / `order_start` / `question_batch`） | 让分支读主图 state（实测读不到：`Send` 的载荷**就是**它的全部输入） |
| 引用核对 | **按来源分档**：`resume`→`raw_text`、`jd`→`jd_text`、`generic` 可选；核不上整题丢弃 | 只认简历原文（实测把验收比例压到 25%，且 jd 槽位永远修不好） |
| 两套闸门的判据 | 出题闸门 `verify_evidence` 与评审规则层共用 `evidence_problem` | 各写一遍 `evidence_belongs`（会出现"generate 按 JD 放行、review 按简历判废"） |
| 难度 | 一律由槽位盖章覆盖，模型自报只记一句流水账 | 采信模型自报（M4 的配比等式立刻作废，见 ADR-0009） |
| 分支失败 | 少出题 + 记 `errors`，差额由 `review` 按数量缺口驱动回退 | 分支抛异常（一次网络抖动崩掉整条图），或分支自己计重试（回退预算双花） |
| 分支 trace | `generate_item` **不**包 `traced()`，模板版本由扇出节点声明一次 | 每分支一步 trace（15 题 → 十几个步骤，把 7 段主干观测面冲成噪声） |
| 评审模型 | 独立 prompt + 独立槽位 `llm_model_review`，`temperature=0.0`，不传生成时的推理 | 复用 generate 槽位/温度（自己评自己，且批注每次不同，门会抖） |
| 评审顺序 | 规则先判整批；规则已超阈值就不调模型 | 每次都调模型（重做后还要再评一遍，白花） |
| 评审失败 | **原样重抛** `LLMError`，并把 `question_batch` 塞进 `details` | 吞掉（等于替一批没人检查过的题开绿灯，AGENTS.md §4.4） |
| 质量门 | 判据唯一来源 `should_redo`，节点与路由函数都调它；空批次算 1.0 | 节点和路由各算一遍占比（会分叉）；空批次算 0.0（整批失败被当成通过） |
| 缺题批注 | 距 `plan.total` 缺几题记几条（`index=None`） | 合并成一条"缺 3 题"（1/12 的占比，门几乎永远关不上） |
| 跨槽位重复 | 载荷带 `roster`（同批其它槽位的 `topic`/`difficulty`/`count`，不含本槽位）+ prompt 硬规则"同主题别档已问基础，本题换层面" | 只靠"同批不许换皮重复"这句话（分支看不见兄弟，稳定复现 5/15=0.33 压在门上） |
| 预算用尽 | `status=aborted`，**一行题目都不写**，批注留在 `interview.review_issues` | 把不合格题也落库（读的人分不清它是坏了还是没跑完） |
| 落库 | 收尾一个事务写 `interview` + N 行 `question`；`latest_batch(interview_id) == batch` 就跳过写题 | 分两次提交（半份报告）；只靠唯一约束兜底（会抛 `IntegrityError` 打断收尾） |

## 理由

1. **失败面要切到能重试的那一层**。扇出之后单条槽位失败只少那一槽的题，重做也只重做失败
   那一档的预算；而"整批 15 题一次调用"的失败面是整份报告。扇出的代价（跨槽位看不见彼此）
   用一份 `roster` 摘要补，比整批重做便宜得多。
2. **`Overwrite` 是扇出与回退唯一能共存的办法**。`operator.add` 通道上，分支只能追加；
   要"换新批次"只能由**扇出节点**在派发之前把通道整批换掉。实测每个 super-step 只允许一个
   `Overwrite`，正好对应"一轮一次扇出"。
3. **引用按来源核对不是放宽，是把口径对准真实的出处**。计划书那句"简历原文引用"写在
   只有 `resume` 一种来源的假设上；M4 的配额表实际会产出 `source=jd` 的槽位（占比 21/26），
   它们的出处本来就在 `jd_text` 里。继续只认简历等于要求这批题永远交白卷。
4. **出题与评审必须同一个判据**：一旦两套闸门对"什么算有依据"各执一词，回退就成了
   无限循环——generate 按 A 标准放行、review 按 B 标准判废，重做多少次都收敛不了。
   `evidence_problem` 就是那个唯一判据。
5. **评审失败重抛、出题分支失败吞掉**看似矛盾，实际是同一原则的两面：判据缺一半就不能开
   绿灯（评审是质量门的另一半），而"少几题"本身正是门要读的**信号**，不是门的故障。
6. **`aborted` 不写题目**：`interview.review_issues` 已经说清了为什么不合格，题目行只会
   让下游 API 误以为有一份可用的报告。留状态、不留内容。

## 权衡与代价

- **分支各出各的题，跨槽位的全局一致性只能靠 `roster` 摘要间接保证**。真正彻底的解法是给
  每条槽位一个互不相同的考察角度——那要改 `plan` 的配额表（M4），已挂 `docs/TODO.md`。
- **回退是整批重做，不是只补失败槽位**。缺口/重复类批注明明只涉及两三题，却要重花 11 次
  调用。改成"定向重做"要在 state 里记每槽位的状态并让 `Send` 只派发需要重做的槽位，
  复杂度值得等 M6 的花费数据出来再定。
- **`fail_ratio` 的分子是批注条数**，模型对同一题报两条就算两个缺陷。目前靠 prompt
  （"只报序号较大的那一题""别因还能更好就报问题"）压住，没有按题去重。真跑数据显示
  误报集中在"评审看不见出处"和"模型判日期"两类，都在 prompt 侧补掉了；按 `index` 去重
  留作下一步，因为它会同时削弱"这道题错得离谱"的严重度信号。
- **`roster` 让每条分支的 prompt 多约 200 token**（11 槽位 × 每槽位一份摘要）。相对整批
  一次运行的 13.7 万 prompt token 是零头，但它是**随槽位数增长**的成本，槽位很多时要改成
  只给同主题的兄弟槽位。
- **`generate_item` 不进 trace**，所以 trace 里看不到"哪条槽位花得最久"。分支的失败与丢弃
  仍然逐条进 `errors`，只是没有耗时数字。真要做逐槽位归因，得给分支单独一步（并接受
  trace 变长）。
- **落库点在 `review` 节点里**（通过 `persist_report` 交给 service），意味着"节点不直连
  数据库"这条铁律的落法是节点持有装配期注入的会话工厂。给 `sessionmaker=None` 时收尾只记
  流水账不落库——图骨架测试与脚本要走这条路，但它也意味着"跑完了却没存下来"是合法配置，
  靠 `errors` 里那句"收尾未落库"提示。

## 后续影响

- M6 的 `scripts/eval_e2e.py` 直接复用 `evidence_ratio` 与 `run_e2e_live.py` 的 PASS/FAIL
  口径；那三个指标（引用比例、题数达标、回退轮数）在这里已经是可计算的函数，不再是文档里的话。
- 后台化（`BackgroundTasks`）之后，`review` 的落库就是任务终态的写入点：`completed` /
  `aborted` 两个状态已经把"能不能读这份报告"编码进库里，轮询接口只需读它。
- 若接真检索（sqlite-vec，阶段 6）或引入第二版出题模板，`prompt_version` 已经按节点记进
  trace，`generate@v1` / `review@v1` 可以直接做 A/B 归因，不用改节点代码。
- 定向重做（只补失败槽位）如果落地，`GenerateJob.roster` 要换成"本批已收题目"的白名单，
  而那时风险 6 的"分支看不见旧题"需要重新论证——因为定向补题必须知道已有题问了什么。
